## Size grouping: actual hard upper limit

- UI takes a positive integer in MB (decimal 1,000,000 bytes), default 2048 MB, minimum 1 MB; backend validates finite integer bytes, range 1,000,000..100,000,000,000, overflow-safe. Reject unknown modes/options. No approximate-size claim disguised as hard cap.
- Final CLOSED file length must be <= configured cap for EVERY part. Mail+attachments stay together; never split a message or strip metadata/content. If one-message PST exceeds cap (including PST overhead), fail the whole job before final publication, explaining required larger size. Never publish an oversized exception as success.
- Size preview shows selected counts and chosen cap; final part count is explicitly determined during writing, unless actually measured. Do not invent an exact predicted count from source size/estimates.
- Bounded, correctness-first implementation for current small/evaluation phase: write/close/verify a candidate subset using the existing converter core; if oversized, discard only that task-owned candidate and partition its ordered physical entry list into smaller subsets, rebuilding until each finalized leaf fits. Deterministic recursive bisection is acceptable. Single-item oversize fails. This may reread/rewrite data and is NOT a scalable 100GB implementation; document that limitation. Do not load all messages/bodies/attachments simultaneously in RAM; retain only metadata/entry identifiers and current-part snapshots.
- Output names `arsiv-001.pst`, `arsiv-002.pst`, etc. Preserve hierarchy, no deduplication. Per-part bytes/hash/counts measured after close.
